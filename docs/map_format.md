# 大富翁8 地图文件格式（.map / .ltm）

解析器：`<workspace>\scripts\mapfmt.py`（`python -I mapfmt.py <文件> [--trace]`）。
验收结果：`<old-edition-dir>\Map\` 下 15 个 .map 与 15 个 .ltm 全部解析到文件末尾，**剩余 0 字节**。
所有字段都对应游戏代码里的一次读取；没有按剩余长度推算大小，也没有把剩余字节当 blob。循环次数全部来自文件里的计数，或来自已解析出的头部值（见各表“依据”）。

函数地址均为 Ghidra 的 `FUN_xxxxxxxx`（RichMan8.exe）。读取原语：
- `.map`：`FUN_0051e120(stream, buf, n)` = RwStreamRead，流由 `FUN_0051e620(2,1,path)` 打开。
- `.ltm`：`FUN_0056abf0(buf, size, count, file)` = fread，文件由 `FUN_0056aa50(path,"rb")` 打开（`FUN_0056abb0` 关闭）。

## 0. 文件之间的关系

| 事项 | 依据 |
|---|---|
| 地图号 → 文件名来自 `Config\stage.bin` 的 `mapfile=`（例如 `[香港] id=1 mapfile=01.map`），`FUN_004a8f80(id)` 按 id 取该条目，`FUN_004a31f0` 拼成 `Map\%s` | `FUN_004a31f0` |
| `.map` 由 `FUN_004a33d0(path, flag)` 读取 | `FUN_004a33d0` |
| `.ltm` 与 `.map` 同名：`FUN_004a31f0` 在 .map 加载成功后，用 `strcpy(path + strlen(path) - 3, "ltm")`（`FUN_005c5280`，字符串在 0x5E392C）把扩展名换成 ltm，再调用 `FUN_004a3670(path)` | `FUN_004a31f0`、`FUN_004a3670` |
| `.ltm` 只在显卡条件满足时读取（`FUN_00401060(5) > 4` 且设备能力 `+0x94 > 2`），段 B 还要求 `(caps+0xC4 & 0xFF00)>>8 > 1` | `FUN_004a3670` |

## 1. .map

整体布局（宽 w、高 h，样本全为 64×64）：

| 段 | 起始偏移（64×64） | 大小 | 元素数及依据 |
|---|---|---|---|
| 魔数 | 0x00 | 8 | 固定 |
| 版本 | 0x08 | 4 | 固定 |
| 头部 | 0x0C | 0x3C | 固定 |
| 顶点网格（地形高度 / 贴图） | 0x48 | (w+1)(h+1)×20 = 84500 | (w+1)(h+1) = 4225（来自头部 w、h） |
| 格子网格（道路 / 事件 / 地块 / 街道 / 地貌贴图） | 0x14ADC | w×h×28 = 114688 | w×h = 4096（来自头部 w、h） |
| 装饰物（article） | 0x30DDC | article_count×0x4C | 头部 +0x08 |
| 水面 | 紧接 | 52（mode=2）/ 0（mode=0） | 头部 +0x38 |

#### 地块放置（2026-11-14 复刻并验证）

`scripts/plots.py` 完整复刻了加载时的地块放置流程：`Map_LoadFromStream_Build`(0x420f90) 按格子序号处理锚点（锚点都是道路格），`Map_PlaceTileObject`(0x424d30) 按 terra.txt 的 size 分到 `Map_PlaceObjCat1..4`。
- n 是“按规则枚举候选位置时取第 n 个”。
- 空闲格的条件：没有道路网格（+0x28）、没有悬崖（+0x20，悬崖码见 `Map_CalcTileCliffCode` 0x4233c0，低 16 位为 0 或命中 `DAT_00604110` 的 8 个缓坡码时算平地），也没有被其他地块占用（+0x5C）。
- 朝向：单格地块查表（上 0°、下 180°、左 90°、右 270°、左上 45°、右下 225°、右上 315°、左下 135°）；多格地块由“地块中心 − 道路格中心”的方向取 45° 的倍数（`Map_CalcObjPlacement` 0x425470）。
- 地块垫片贴图为 `terra\dichange_h/b/q_0.tga`，UV 生成方式见 `Map_BuildObjPadMesh`(0x4266e0) 和 `Map_BuildObjPadMeshXform`(0x426c90)。
- 验证：15 张图共 770 个锚点全部恰好在第 n 个候选处落位（含 n=2、3、4 的情况），渲染结果中地块都紧贴道路、落在平地上。
- 近似：奇数级别顶点的“3”标记分支没有复刻（46 个顶点），但不影响上述验证结果。
- 新开局时，每条街随机给 1/3 的住宅地建 1~3 级住宅（`Unk_GameLoop_f0d00` 0x4f0d00 → `Land_OnEnter` 0x4ef580；stage 的 clime>1 时 art id 再 +5）。
- 事件格上放事件牌（event.bin 的 artId，旋转 −45°，循环播放 3 号动作；`Unk_ObjectCreate_ee230`）。

- 水类 `CWater`（vtable 0x5E194C，由 `FUN_00479d50` 构造）的 `[11]` = `FUN_00477230`：不看 mode 参数，读 8 项共 52 字节。

所以不论显卡档次，mode==2 都消耗 52 字节，文件格式与硬件无关。样本中没有 mode=1 的文件，mode≠2 的 4 字节分支只是按代码实现，未经样本验证。

## 2. .ltm（光照贴图）

结构：`段 A`（地形光照贴图）+ `段 B`（装饰物光照贴图）。两段的单个元素格式相同，由 `FUN_004322f0` 读取。

```
i32 nA
nA × 光照贴图
i32 nB
nB × 光照贴图
```

光照贴图（单个，12 + w×h + 64 字节）：

| 偏移 | 类型 | 含义 | 依据 | 把握 |
|---|---|---|---|---|
| +0x00 | i32 | 编号（对象 +0x44）。段 A = 地形四叉树叶节点编号；段 B = article 在 .map 里的序号 | `FUN_004322f0`：`fread(obj+0x44,4,1)` | 见下 |
| +0x04 | i32 | 宽 w（样本 A=256、B=64） | `fread(&w,4,1)` | 高 |
| +0x08 | i32 | 高 h（样本 A=256、B=64） | `fread(&h,4,1)` | 高 |
| +0x0C | u8[w×h] | 8 位灰度光照值（A 范围 96~255，B 范围 80~166） | 两条分支都读 w×h 字节：`FUN_005202a0(w,h,8,0x404)` 建 LUM8 纹理光栅并 `RwRasterLock`（`FUN_00520340`）后 `fread(raster,1,w*h)`；失败则用 `FUN_005202a0(w,h,0,4)` + 临时缓冲，再把每个字节展开成 4 字节像素 | 高 |
| 之后 | f32[16] | 64 字节：4×4 浮点矩阵，形状与 RenderWare 的 RwMatrix 一致（right/flags/up/pad/at/pad/pos/pad，第 4、8、12、16 个值是未初始化的 pad，样本里常是 -2.0e18 之类的垃圾）。用途是光照贴图的投影/变换矩阵；段 B 的该矩阵被复制到 article 内存结构 +0x80，由 `FUN_00441d50` 返回给渲染 | `FUN_004322f0`：`fread(obj+4,1,0x40)`；`FUN_0043bdf0` 把栈对象里的 16 个 dword 拷到 `article+0x80`；写出函数 `FUN_00432220` 对称（`FUN_0056ac20`） | 位置与大小：高；“RwMatrix 形态/投影矩阵”：中 |

段落依据：
- 段 A：`FUN_004a3670` → `FUN_00420790` → `FUN_00431f00`：`fread(&n,4,1)`，循环 n 次，每次 `FUN_004322f0`。样本里 n 恒为 64。
- 段 B：`FUN_004a3670` 里 `(caps+0xC4 & 0xFF00)>>8 > 1` 时调 CArticleMgr 的 `+0x38` = `FUN_0043bdf0`：`fread(&n,4,1)`，循环 n 次，每次 `FUN_004322f0`（对象在栈上，编号 = article 序号）。n 是 .map 里 article_count 的子集（样本 19~173）。

编号含义（用数据与代码对照）：
- 段 A 的 64 个编号恒为 `4-7,9-12,14-17,19-22,25-28,…,82-85`。`FUN_0042dfe0/FUN_0042fe50` 把地形包围盒（x∈±w·25、z∈±h·25、y∈[-100,100]）反复四分，直到对角线 ≤ 800，节点编号用计数器 `DAT_00604130`（从 1 起）先序递增。64×64 地图四分三次得到 64 个叶子（每个覆盖 8×8 格，400×400 世界单位），其先序叶编号恰好就是上面这组。mapfmt.py 用同一规则复算，15 个样本全部吻合（输出里的 `check_A_ids_equal_quadtree_leaf_ids`）。`FUN_00431fc0`/`FUN_00432080` 按 +0x44 编号查找光照贴图。把握：高（代码规则 + 数据一致；没有追到“渲染叶节点时按 id 取用”的那一处调用）。
- 段 B 的编号集合 恒等于 .map 里 article[11]≠0 的 article 序号集合（输出里的 `check_B_ids_equal_map_articles_with_flag11`，15 个样本全部为 true）。`FUN_0043bdf0` 用它作为 article 序号写 `article[id]+0xC0/+0x7C/+0x80`。把握：高。

文件大小核对：段 A 固定 4 + 64×(12+65536+64) = 4,199,172 字节（64 个 256×256）；段 B 为 4 + nB×(12+4096+64)。例如 01.ltm：4,199,172 + 4 + 133×4,172 = 4,754,052，与文件大小吻合。

叶子位置与光照贴图 UV（2026-11-14 渲染整图时修正，已验证）：
- `Map_InitGrid`（0x420cb0）传给 `QuadTree_Build` 的根盒子是**反向**的：p0 = (+w·25, 100, +h·25)，p1 = (−w·25, −100, −h·25)。子节点按 (中心..p1)、(p0..中心)、(p0.x,中心.z .. 中心.x,p1.z)、(中心.x,p0.z .. p1.x,中心.z) 生成，所以第 0 个子节点是 (x−, z−) 象限。早先按 min<max 建树会使所有叶子整体旋转 180°（编号集合不变，所以 id 检查发现不了）。
- 段 A 矩阵就是普通 RwMatrix 仿射变换：`u = x·m[0] + y·m[4] + z·m[8] + m[12]`，`v = x·m[1] + y·m[5] + z·m[9] + m[13]`。15 张地图全部 64 个叶子中心映射到 (0.5, 0.5)（误差 ≤ 0.012，来自取 y=0）。
- 交叉验证（地图 01）：物件位置处的光照图暗度均值，旧映射 14.1，修正后 34.1；物件与道路格、地形高度在同一坐标系（压路率 1%，|y−高度| 中位数 0）。
